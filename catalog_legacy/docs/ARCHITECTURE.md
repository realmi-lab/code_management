# 구조와 데이터 계약

## 목적

기획자가 알림의 상황을 설명하면 등록된 코드번호·원문·사용 조건을 찾는다. 새 문구를 작성할 때는 기존 항목을 비교하고, 정식 번호를 만들기 전에 검토한다. Git 소스코드를 읽거나 실행하지 않는다.

## 실행 구성

브라우저 → FastAPI → SQLite 카탈로그

검색은 번호 직접 조회와 관련 문구 검색으로 나눈다. 관련 문구는 기본 모드에서 도메인 키워드 별칭 + 문자 2-gram 유사도를 사용한다. AI 임베딩이 연결된 경우 임베딩 후보를 추가하고, 실제 원본 RRFCombiner로 순위를 결합한다. RRF 값은 정답 확률이 아니며 UI에 신뢰도 백분율을 표시하지 않는다.

원문과 코드번호는 DB 행에서 출력한다. 모델은 원문을 대신 작성하거나 기존 코드번호를 생성하지 않는다. AI의 문장 다듬기는 선택적으로 적용하며 초안으로만 저장한다. 쓰기 작업을 자유로운 LLM 도구 선택에 위임하지 않는다.

## 주요 테이블

- `codes`: namespace + code 유일키, 원문, 메뉴, 노출 조건, 비고, 사용 상태, 원본 근거, 개정 번호.
- `drafts`: 신규 또는 기존 코드의 변경 초안, 대상 코드 개정 번호, 작성/외부 등록 요청/등록 완료 상태.
- `imports`: 미리보기 스냅샷, 파일 해시, 그 시점의 목록 버전, 1회 반영 상태.
- `audit`: 변경 전·후·이유. 별도 개인 사용자 계정 식별은 없음.
- `sequences`: 명시적으로 설정된 접두어별 발급 순번.
- `embeddings`: 항목 ID + 모델/엔드포인트 식별 해시 + 내용 지문 + 검색 벡터.
- `meta`: 스키마 버전 및 카탈로그 버전.

## 불변 조건

1. 실제 목록에 데모 행을 자동 삽입하지 않는다.
2. 검색으로 없는 코드번호를 발급하지 않는다.
3. 문구 표시·복사에서 등록된 띄어쓰기·줄바꿈·자리표시자를 변경하지 않는다.
4. 엑셀의 수식을 실행하거나 임의의 캐시값을 정답으로 취급하지 않는다.
5. 원문 충돌은 자동으로 덮어쓰지 않는다. 개별 선택과 사유가 있을 때만 반영한다.
6. 가져오기에서 빠진 기존 코드를 자동 삭제하지 않는다.
7. 신규 초안은 정식 코드가 아니다. 엑셀 기준 모드에서 앱이 번호를 발급하지 않는다.
8. 정식 등록은 `BEGIN IMMEDIATE` 트랜잭션, 유일 제약, 최신 목록 버전 검사 아래 실행한다.
9. 폐기 번호도 새 항목에 재사용하지 않는다.
10. 기존 문구 변경은 원본 개정 번호를 검사하고 기록을 남긴다.

## 처리 범위

- 정확한 번호 조회는 폐기 항목도 상태와 함께 보여준다.
- 일반 검색은 기본적으로 폐기 항목을 제외한다.
- 상황 검색은 불완전한 질문을 완성된 규격으로 취급해 충돌 판정을 하지 않는다.
- 문구 비교는 별도 단계이며 이후/이내, 시간 단위, 일부 부정 표현, 변수 차이를 검사한다.
- 비슷한 표현이어도 메뉴·노출 조건이 없으면 재사용 확정으로 표현하지 않는다.
- 한 줄에 하나의 코드번호 또는 문구를 넣는 기획서 검토를 제공한다. 완전한 문서 이해·정책 판정은 범위 밖이다.

## 모델 연결

외부 모델은 서버 환경변수로만 설정하며 브라우저 요청이 임의의 모델 주소를 선택할 수 없다. URL 사용자정보, 리다이렉트, 비HTTPS 외부 주소를 거절한다. 비로컬 주소는 `AI_ALLOW_EXTERNAL=true`가 있어야 한다. 외부 주소 허용은 운영자의 자료 전송 승인과 별도로 확인해야 한다.

임베딩은 관리자가 UI에서 명시적으로 생성을 시작한다. 검색은 데이터 최신 지문을 확인하고 없는 벡터를 기존 벡터로 가장하지 않는다. 일부 벡터가 없거나 오류가 있으면 기본 검색을 병행한다. 원문 변경 시 저장 벡터를 제거한다.

## 확장 지점

실제 엑셀의 필드·코드 발급 규칙 확정 → 검색 정답 사례 구축 → 조직 인증·역할 기반 승인 → 다국어와 코드 범위 분리 → 승인된 최신 엑셀-초안 연결 → 실제 코드 사용처 연결 → 데이터 규모에 따른 PGVector/Nori/리랭커 도입 순서로 확장할 수 있다. 이는 구현 완료 목록이 아니라 후속 설계 항목이다.
