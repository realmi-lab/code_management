# Apple 온디바이스 실사용 검토와 검색 결과 보존

기준: 2026-09-22, 이 Mac(macOS 26.5.1)의 Docker 서비스와 호스트 FoundationModels 브리지. 모든 실험 자료는 demo 합성 DB이며 회사 자료 검증이 아니다.

## 결론과 현재 설정

현재 알림 카탈로그 대화의 주력 생성·판정 모델로 Apple을 권하지 않는다. 개선 후 12개 질문을 두 번씩 실행한 24회 중 조건을 충족한 답변은 **2회**, 나머지 **22회는 입력 한도 초과**였다. 통과한 두 번도 동일한 코드 2건의 시간 방향 비교였다. 작은 비교의 성공을 일반 대화·최종 판정의 신뢰성으로 확대할 수 없다.

사용자가 후보·표시 데이터를 줄이는 Apple 최적화를 중단하고 이전 DeepSeek로 변경하도록 지시했다. 최종 실행 설정은 **Command Code 경유 `deepseek/deepseek-v4.1-flash`**, 생성·판정 모두 동일, reasoning_effort=low이다. Apple 때문에 검색 후보를 4건으로 제한하는 코드는 최종 배포에 없다. Apple 추가 튜닝·추가 벤치마크는 중단했다.

## 실제 측정

| 검사 | 결과 | 해석 |
|---|---|---|
| 변경 전 첫 5개 질문 | 5/5 `unsupportedLanguageOrLocale` | 준비 상태가 실제 요청 성공을 보장하지 않음 |
| 중복 메타데이터·스키마 안내 정리 후 12질문 × 2회 | 유효 답변 2/24, 입력 초과 22/24 | 후보 20~39건 전체를 전달하는 현재 검색 설정에서 부적합 |
| 코드 2건 비교 | 2/2 통과 | “30초 이후”와 “30초 이내” 차이 설명; 단일 문항 반복 결과 |
| DeepSeek로 변경 후 브라우저 실제 질문 | 원문·메뉴·조건 포함 답변, 후보 25건 | 생성 후 검증 및 근거 재작성 1회까지 완료 |
| DeepSeek 해당 턴 시간 | 66.420초 | 외부 모델 생성·두 판정·재작성 비용이 큼. 빠르다고 결론 내릴 수 없음 |
| 전체 수치 조건 목록 | 42/42건 표시 | DB 원문 직접 조회, 모델 입력 한도와 독립 |

24회 모두 HTTP 200인 이유는 검색이 성공했을 때 AI 설명 실패를 별도 `ai_error`로 표시하고 DB 후보를 돌려주도록 개선했기 때문이다. **HTTP 성공 24/24는 AI 성공 24/24가 아니다.** 오류 답변을 정상 생성으로 저장하지 않으며 `ai_used=false`로 구분한다. 실제 검색 엔진 오류·버전 충돌은 여전히 실패로 반환한다.

유효 답변 판정: HTTP 정상 + ai_error 없음 + 예상 코드가 후보에 있음 + 해당 DB 문구를 답변에 포함. 무관 질문은 빈 후보, 비교는 두 시간 방향 보존을 검사했다. 넓은 30초 질문은 수치 포함을 검사했으나 해당 두 실행은 모두 모델 오류로 실패했다. 후보를 반환했다는 사실만으로 질문 관련성을 보증하지 않는다. 5회 사전 검사와 24회 후속 검사는 동일 크기의 대조군이 아니다.

이번 결과는 이 Mac·현재 OS·현재 데이터·현재 어댑터의 관측이다. Apple Intelligence 전체 기능이나 향후 OS 모델의 성능을 일반화하지 않는다. 판정만의 별도 정확도/오답 차단 반복 벤치는 이번 사용자 중단 지시 뒤 추가 실행하지 않았다.

## 원인과 적용한 개선

- **화면 데이터와 모델의 성공을 분리했다.** 검색된 후보는 전부 표시하고 AI 설명 실패를 명시한다. 새 대화의 명백한 찾기 요청은 불필요한 의도 분류 호출을 생략한다. 후속 질문·비교·초안 분류는 유지한다.
- **상위 검색 후보 수와 전체 수치 일치 수를 구분했다.** `GET /api/code-catalog/quantity-matches`에서 문구·메뉴·노출 조건에 있는 정확한 수치/단위를 검사하고 20건씩 보여준다. 30초와 130초/30분을 구분하며 active 코드만 포함한다. 서브에이전트가 발견한 천단위 쉼표 오류도 수정해 1,000원은 1000원과 일치하고 9,000원과 불일치한다. 복수 수치 조건은 AND이다. 이는 모든 의미상 관련 코드의 개수를 뜻하지 않는다.
- **원본 검색 설정을 유지했다.** E5 768→1536 + PGVector, Nori, RRF, bge-reranker-v2-m3-ko를 그대로 사용한다. 현재 저장된 retriever_top_k=20, reranker_top_k=50이며 넓은 질문의 RRF·리랭커 결과는 25건이다. 이전 기록의 “최종 8건/리랭킹 12건”을 현재 상태로 간주하면 안 된다. 이 작업은 이 설정값을 변경하지 않았다.
- **근거 검사를 보완했다.** 사용자 질문의 주장·숫자가 등록된 DB 사실의 근거로 통과하지 않도록 설명 검증 근거를 catalog/rule_comparison으로 한정했다. 임계값은 그대로다.
- **불필요한 입력만 제거했다.** 대화 이력에서 UI 집계/오류 메타데이터를 모델에 다시 보내지 않는다. Apple용 전송에서 내부 UUID·수정 시각·중복 저장 메타데이터와 중복 스키마 안내를 줄였으나 코드·문구·메뉴·조건을 삭제하지 않았다. 이 변경만으로 현재 검색량의 입력 한도는 해결되지 않았다.

Apple 공식 문서는 온디바이스 모델의 세션 컨텍스트 한도와 한국어 등의 높은 문자당 토큰 사용을 설명하며, 요약·추출·분류처럼 작은 작업으로 나누는 사용 방식을 제시한다. 현재 서비스는 많은 후보를 함께 비교하는 요구가 있으므로 이번 실측에 따라 DeepSeek로 복귀했다. [컨텍스트 문서](https://developer.apple.com/documentation/technotes/tn3193-managing-the-on-device-foundation-model-s-context-window), [Apple의 모델 사용 범위 설명](https://developer.apple.com/videos/play/wwdc2025/286/).

## 검증과 한계

확장/API pytest **311개**, 설치 unittest **77개**, 대역 인증·모델 기반 native HTTP **10개**, JS 구문 검사 통과. 원본 384개 파일·모드 일치. API·worker·beat 재배포 완료, 3개 서비스 각각 핵심 파일 9개의 호스트/컨테이너 해시 일치. 마지막 빌드는 Docker 캐시 lease 오류로 한 번 실패했지만 재시도 후 정상 완료했다. 전체 검사 재실행 중 지연으로 중단한 로그는 별도 보존했으며, 최종 전체 재실행은 311개 모두 통과했다.

실제 인앱 브라우저에서 DeepSeek 선택, 30초 검색의 생성·검증 완료, 전체 목록 20→40→42건, 42개 상세 버튼, AT-1923 원문 상세를 확인했다. 전체 목록의 페이지를 여는 작업은 AI를 호출하지 않는다. 목록 버전 변경 시 오래된 페이지를 섞지 않고 409로 다시 검색을 요청한다. DB 전체 조회 기반의 수치 목록은 현재 300건 샘플에서 검증했으며 대규모 데이터의 부하 검사는 하지 않았다.

증거 폴더: [apple-usability-2026-09-22](verification/apple-usability-2026-09-22/). `before.json`, `after.json`은 Apple 실행, `deepseek-ui-thread.json`·`deepseek-metrics.log`는 전환 후 실제 턴, `quantity-page.json`은 수치 전체 목록, `all-42-visible.png`는 실제 화면이다. 모델 설정은 `final-provider.json`, 검색 설정은 `search-settings.json`에 보존했다. 새 커밋은 만들지 않았다.
