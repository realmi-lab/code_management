원본의 검색 모드·HyDE·멀티쿼리·청킹 선택값은 DB/캐시에 보존하고, 실행 시 복사본에만 임베딩 제약을 적용한다. 임베딩이 없을 때도 관리 화면에서 향후 사용할 값을 저장할 수 있다. 임베딩 연결 후 일반 문서와 카탈로그를 재인덱싱하면 해당 옵션이 적용된다. 설정 화면의 선택값과 실제 키워드 실행 상태를 안내 문구로 구분한다. 원본과의 기능별 연결 및 원본 자체 미완성 부분은 [기능 비교](FUNCTIONAL_PARITY.md)에 기록한다.

## 2026-09-21 AI 공급자와 검색 방식 선택

관리자 전용 `/api/code-catalog/ai-settings`에서 DeepSeek 직접 API, Command Code 경유 DeepSeek, Anthropic Claude, OpenAI를 선택한다. 모델명과 검색 방식도 저장하며 원본 `get_current_user`의 관리자 권한 및 설정 version을 검사한다. 키는 서버의 전용 `ai-settings` 볼륨에 권한 0600인 파일로 원자적으로 저장한다. 읽기 응답에는 키 원문 없이 공급자별 등록 여부만 반환한다. `.env`는 초기값이며 저장된 관리자 설정이 우선한다.

`deploy/patch_provider.py`가 원본 빌드 사본에 `RoutingLLM`/`RoutingEmbedding`을 연결한다. 다음 호출부터 선택값을 읽으며 Claude는 원본 Anthropic Messages 클라이언트를 사용한다. OpenAI 호환 주소로 Claude 요청을 보내지 않는다. 키 누락/제공자 오류에서 다른 공급자로 자동 전환하지 않는다. 기본 모델과 실제 호출 검증 범위는 [AI 설정 안내](AI_SETTINGS.md)에 기록한다.

임베딩은 독립적으로 `none` / `local` / `openai`를 선택한다. `none`은 원본 Nori 키워드 검색을 명시적으로 선택하며 벡터 검색·HyDE·멀티쿼리와 임베딩 기반 RAGAS 평가를 사용하지 않는다. 임베딩 벡터를 가짜 숫자로 채우지 않고 벡터 열을 NULL로 저장한다. `local`은 고정 revision의 multilingual-e5-base를 같은 Mac의 Docker 서비스에서 실행한다. 768차원 정규화 벡터 뒤에 0을 붙여 원본 1536차원 저장 계약을 유지하며 코사인 유사도는 보존한다. `openai`는 text-embedding-3-small과 OpenAI 키를 사용한다.

검색 방식/임베딩 모델을 변경하면 카탈로그 검색 준비와 일반 문서 재인덱싱이 필요하다. 카탈로그는 모델·PII 정책 식별자가 현재 공개 스냅샷과 다르면 검색을 거절한다. 로컬 서비스가 준비되지 않았거나 인덱스가 실패하면 오류를 표시하며 다른 검색 방식으로 몰래 전환하지 않는다.

## 1. 실제 실행 연결

원본 frontend 전체 + `/codes` 페이지 → 같은 출처의 카탈로그 작업실 → 원본 FastAPI app에 추가한 `/api/code-catalog` → 동일 PostgreSQL의 cm_* 테이블.

기본 `CODE_AUTH_MODE=local`은 사용자 요청에 따라 로그인·관리자 비밀번호 입력을 없앤 로컬 공용 작업실이다. 원본 DB의 실제 단일 로컬 관리자 User를 원본 `get_current_user` 경로에서 반환한다. 모든 접속자가 같은 관리자 권한과 사용자 ID를 공유하며 body의 사용자 ID/role은 신뢰하지 않는다. 원본 화면·검색 엔진·DB는 유지하고 빌드 사본의 변경을 `deploy/patch_*`로 추적한다.

선택형 `CODE_AUTH_MODE=jwt`는 원본 로그인·AuthProvider·JWT 권한 검사를 유지한다. 이 모드의 작업실 JWT는 메모리에서 origin/source 검증한 postMessage로 전달하며 토큰 만료 시 부모의 refreshAccessToken을 요청한다. UI 프레임 경로만 SAMEORIGIN/frame-ancestors 'self'를 허용한다.

## 2. 원본 검색 엔진을 사용하는 범위

상황 검색은 선택한 검색 모드에 따라 원본 HybridSearchOrchestrator에 다음 구성 요소를 연결한다.

- 선택한 공급자로 연결되는 원본 임베딩·LLM 인터페이스와 기존 한국어 리랭커 인스턴스. 키워드 모드에서는 임베딩을 호출하지 않는다.
- 원본 VectorSearchEngine을 상속하고 SQL 대상만 cm_search_chunks로 바꾼 엔진.
- 원본 ElasticsearchNoriEngine을 상속하고 인덱스만 cm_catalog_chunks_v1로 바꾼 엔진.
- 원본의 RRF·질문 분류·멀티쿼리·HyDE·문서 범위·리랭킹·입력 검사 등의 검색 처리.
- 원본 Langfuse 모니터.

원본 검색에는 generate_answer=False를 전달한다. 번호와 원문을 자유 생성하지 않기 위해 검색 결과를 현재 cm_codes로 검증한 뒤 별도의 제한된 설명/초안 프롬프트를 원본 LLM에 전달한다. **일반 문서 답변과 카탈로그 답변 프롬프트는 다르다.** 카탈로그 설명/생성 문구에는 별도 `CatalogSafety`가 원본 숫자·충실도·환각 검사기를 호출한다. 판정 형식이 잘못되거나 실패 판정이면 저장하지 않는다. 조회되지 않은 ID, 변경된 숫자·변수도 추가 검사하지만 모든 업무 의미의 완전성을 보장하지 않는다.

자동 분류에서 `draft`가 나와도 인용 문구 밖에 명시적인 작성·수정 지시가 없으면 기존 코드 검색으로 처리한다. 상황 설명이나 문구 안의 명령형은 초안 작성 권한이 아니다. 명시적으로 선택한 `action=draft`와 샘플의 초안 금지는 유지한다.

설명(`Explanation`)의 수치·근거 검증 실패 또는 JSON 스키마 오류는 동일한 근거로 한 번만 다시 생성한다. 오류 종류별로 재시도 횟수를 늘리지 않으며 한 요청의 설명 생성은 최대 두 번이다. 수정한 답변도 원본 숫자 검사와 충실도 0.9·근거 0.8 기준을 모두 통과해야 저장한다. 같은 답변을 다시 생성하면 검증 모델에 재채점을 요청하지 않고 차단한다. 검증 모델의 잘못된 형식·통신 오류, 개인정보·입력 방어 실패와 초안 작성에는 이 재생성을 적용하지 않는다. 실패한 답변/검증 의견을 신뢰할 근거로 추가하지 않으며 스키마 진단 로그에는 오류 종류와 알려진 필드명만 남긴다.

원본의 일반 `/api/search`와 생성/평가 경로는 그대로 존재한다. 검색 준비가 안 되었을 때 문자 유사 검색으로 대체하지 않으며 명확한 오류를 반환한다. 원본 기본 단계는 관리자 RAG 설정으로 제어한다.

## 3. 데이터와 인덱스 일관성

cm_codes는 코드번호 유일 제약, 원문, 메뉴, 조건, 상태, 개정 번호, 원본 셀 근거를 저장한다. cm_state는 catalogue version과 공개 index snapshot/version/model을 저장한다.

등록/변경/import 확정 → catalogue version 증가 → Celery 작업 → PostgreSQL 검색 행과 ES Nori에 **같은 chunk UUID**로 새 스냅샷 작성 → bulk 오류 확인/refresh → 버전이 그대로일 때만 새 스냅샷 공개. 의미 검색 모드에서는 벡터도 함께 저장하고 키워드 모드에서는 임베딩을 호출하지 않는다. 검색용 복사본의 PII를 가리되 등록 원문 DB는 변경하지 않는다.

작업자 간 PostgreSQL advisory lock을 사용한다. 중간 실패한 인덱스는 활성 포인터가 없어 검색하지 못한다. 조회 직전/직후 버전이 달라지면 재검색을 요구한다. 검색 결과의 코드·개정 번호를 원문 DB와 대조하고 원문은 DB에서 반환한다. 폐기 항목은 일반 검색 인덱스에서 제외하고 번호 직접 조회에서는 상태를 표시한다.

실패 후 반복적인 유료 임베딩을 막기 위해 index_error가 있으면 주기 재시도를 멈춘다. 관리자가 검색 준비를 다시 요청할 수 있다. 생성 중 목록이 변경된 스냅샷은 공개하지 않는다. ES에 남는 비공개 고아 스냅샷과 과거 스냅샷의 장기 정리·보관 정책은 운영 과제로 남아 있다.

## 4. 대화 흐름

한 번의 턴은 제한된 작업 흐름이다. 모델이 등록·삭제 API를 마음대로 호출하는 무제한 도구 에이전트가 아니다.

1. 사용자/대화 소유권과 요청 ID, 대화 version을 확인한다.
2. 단순 번호 조회는 직접 처리한다. 다른 질문은 원본 LLM으로 search/compare/draft/explain을 분류한다.
3. 이전 후보 순서, 선택한 코드, 최근 대화, 직전 초안을 근거로 후속 질문을 해석한다.
4. 검색은 실제 원본 검색 어댑터로 처리한다. 비교는 사용자 표시 문구를 대상으로 조건 규칙과 AI 설명을 결합한다.
5. 새 문구는 초안만 생성한다. 생성 문구로 기존 항목을 다시 검색하고 비교한 뒤 저장한다.
6. 결과와 초안은 최신 카탈로그 version 및 대화 CAS 아래 한 트랜잭션으로 저장한다.

동일 request_id 재전송은 기존 결과를 반환한다. 같은 ID에 다른 내용은 거절한다. 동시에 같은 대화를 처리하는 요청, 목록 변경 중 결과, 다른 사용자의 대화는 차단한다. 후보 설명/비교 후에도 원래 검색 순서를 유지한다. '3번 실패' 같은 횟수를 '3번째 후보'로 해석하지 않는다.

입력한 표시 문구는 그대로 보존한다. 모델 planner가 사용자가 적지 않은 비교 문구를 만들면 거절한다. 원문·조건을 바꾸려는 요청이 모호하면 자동 정책 결정보다 명시적 입력/재검토를 요구한다. 정식 등록은 이 흐름에 포함되지 않는다.

## 5. 권한과 승인

원본 get_current_user의 실제 User.id/role를 사용한다. 기본 로컬 모드에서는 모두 단일 관리자 신원을 사용하므로 개인별 대화 격리가 없다. 선택형 JWT 모드의 로그인 사용자는 공유 카탈로그와 자기 대화/초안을 사용한다. 관리자는 가져오기, 코드 수정/폐기, 인덱싱, 전체 초안 검토/등록, 감사 로그를 처리한다. 관리자는 다른 사용자의 개인 대화 본문을 읽는 경로가 없다.

등록은 관리자, 승인 사유, 초안 개정, 최신 목록 버전, 사용된/폐기 번호 중복, 유사 후보 확인을 검사한다. Excel 공식 모드에서는 외부 엑셀 절차의 번호 확정 확인이 추가된다. 번호는 관리자가 입력하며 자동 발급 규칙/시퀀스 서비스는 이 통합판에서 사용하지 않는다.

승인 후 대화를 다시 열 때 초안의 현재 등록 상태를 DB에서 읽는다. 감사 로그에는 사용자 ID와 변경 전후·사유를 남긴다. 사용자 ID가 원본 계정과 연결되지만 계정 삭제/장기 감사 보존/승인자 두 명 정책은 별도 운영 설계가 필요하다.

## 6. 원본·설치 결함 수정

설치기: 검증한 .env를 자식 프로세스에도 동일 적용, 명시적 Compose 프로젝트, 숫자로 정규화한 포트 중복 검사, JWT 모드의 관리자 비밀번호 정책 검사, Redis 비밀번호 URL 인코딩, 검사 실패도 최신 결과 파일에 기록.

원본 컨테이너 사본: 검색 캐시에 generate_answer 반영; 초기 LLM에 실제 설정 모델/온도 반영; 평가 실행 요청자의 ID를 워커로 전달하고 원본 JWT로 내부 API 호출; HTTP 실패 즉시 raise; 실제 평가 설정 snapshot; 문서 삭제 전 ES 정리. 각 수정은 정확한 원본 문자열 개수를 검사하고 변경 전후 해시를 기록한다. 원본 전체 버그 수정/보안 감사는 아니다.

## 7. 요청 제한·캐시·추적

카탈로그 API는 Redis 원자 연산으로 사용자별 분당 대화 30회, 초안 검토 10회, 검색 준비 3회, 가져오기 10회를 제한한다. 제한 서비스를 확인할 수 없으면 요청을 중단한다. 검색 캐시는 원문 대신 코드/개정 참조를 최대 300초 저장하고, 질문·목록 버전·스냅샷·모델·검색 설정·PII 정책으로 키를 구분한다. 캐시 오류에서는 실제 검색을 수행하고 캐시 참조도 최신 DB와 재검사한다.

카탈로그 턴과 모델 단계의 추적에는 원문 대신 상태·모델·시간·반환된 토큰 사용량을 기록한다. 추적 오류가 완료된 작업을 실패시키지는 않는다. 비용 금액 계산이나 모든 원본 문서 경로의 개인정보 감사를 완료한 것은 아니다.

## 8. 알려진 검증 경계

SQLite/대역 기반 도메인·API·어댑터 검증, 실제 loopback HTTP 및 Chromium UI 검사, 전체 Docker 서비스 기동, 실제 Command Code 호출, 실제 로컬 E5 임베딩, 일회성 pgvector PostgreSQL만 붙인 원본 pytest 스위트(`scripts/test_upstream.py`, Redis·Elasticsearch·외부 모델 없음)를 각각 구분한다. 현재 결과는 [검증 보고서](TEST_REPORT.md)에 기록한다. 전체 카탈로그를 실제 PGVector/Nori/LLM으로 검색·비교·초안·승인하는 종단간 검증, 모든 공급자의 실제 키 호출, 검색 품질 평가, PostgreSQL 동시 부하·장기 인덱스 정리·백업/복원은 별도 검증 대상이다.

## GitHub 메뉴 복원과 읽기 전용 검토

`POST /api/code-catalog/compare`, `/review`는 원본 인증 actor 및 검토 요청 한도를 사용한다. 검토는 등록·대화 저장을 실행하지 않으며, 운영 카탈로그 버전이 검토 중 바뀌면 결과를 거절한다. 기본 `catalog_rules`는 명시적인 원문·규칙 비교 기능이고 `semantic`은 기존 UrstoryGateway를 사용한다. 의미 검색 실패를 규칙 결과로 대체하지 않는다.

목록·상세·CSV·비교·기획서 검토의 `namespace=demo`는 합성 JSON 300건(고정 GitHub 예시 16건 + 추가 합성 284건)을 SHA-256 검증 후 읽는다. 운영 DB·인덱스·승인/가져오기 경로는 이 namespace로 바뀌지 않는다. UI에서 샘플 선택은 위 조회/검토 메뉴에만 적용되며 샘플의 정식 등록 기능은 제공하지 않는다. 샘플 대화 검색은 아래 전용 스코프를 사용한다. 업무구분·타입·용도·타이틀·영문 항목은 `source.catalog_fields`에 원문 그대로 보존한다. 가져오기에 없는 선택 열은 기존 값을 유지하고 명시적으로 바뀐 값은 충돌 검토 대상으로 처리한다.

파일 가져오기 화면과 관련 UI 이벤트는 제거했다. 기존 가져오기 API의 보호 장치는 유지한다. JSON 내보내기는 원본 인증을 거친 뒤 선택한 namespace의 전체 목록과 schema_version·synthetic 표시를 반환한다. 기본 화면 조회 대상은 JSON 샘플이며 운영 DB에는 삽입하지 않는다.

## 샘플 대화의 검색·기록 스코프

`SampleStore`는 무결성을 확인한 JSON 원문을 읽고 검색 공개 상태를 `cm_sample_state`에서 관리한다. `cm_thread_scopes`가 대화 소유권과 함께 production/demo 경계를 고정하며, 기존 매핑 없는 대화는 production으로 취급한다. 같은 번호가 양쪽에 있어도 선택한 대화 스코프의 원문만 반환한다. 신규 샘플 테이블은 추가 방식으로 생성하며 기존 대화·목록을 삭제하거나 이관하지 않는다.

샘플의 `UrstoryGateway`는 원본 검색 엔진·설정·AI 공급자를 사용한다. Nori 인덱스는 `cm_catalog_chunks_v1__demo`로 분리하고 PostgreSQL 검색 청크는 스코프별 독립 UUID 스냅샷으로 제한한다. 상태 테이블·검색 캐시·작업자 잠금도 별도로 처리한다. 카탈로그 해시가 바뀌면 샘플 버전을 올리고 재인덱싱을 요구한다. 실패한 인덱스와 다른 목록의 결과로 대체하지 않는다. 선택한 인증 actor, 대화 소유권, 요청 재전송 멱등성, 버전 검사, 요청 제한을 유지한다. 샘플 대화에서는 정식 등록용 초안 생성을 거절한다.

대화 API는 최대 240초를 기다리지만 원본 Next rewrite 프록시 기본값은 30초여서, 서버가 작업을 계속하는 중 화면에 500/ECONNRESET이 발생할 수 있었다. `deploy/patch_proxy_timeout_frontend.mjs`가 고정 Next 설정의 빌드 사본만 수정하여 프록시를 300초로 맞춘다. 변경 전후 해시를 기록하고 원본 계약이 바뀌면 빌드를 중단한다.

AI 응답 충실도와 근거 검사는 같은 답변/근거에 대해 독립적으로 실행하므로 동시 실행한다. 두 검사 모두 성공해야 저장하며 한쪽 실패·예외를 성공으로 취급하지 않는다. 단계별 모델 호출 시간과 전체 시간을 텍스트·키 없이 로그로 기록한다.

## 업무 컬럼 마이그레이션

`Store.initialize()`는 기존 cm_codes에 업무 필드를 추가하고 과거 원문을 title로 옮긴다. 생성 컬럼 message_code는 code와 불일치할 수 없다. 원본 기록과 이력은 보존하며 기존 날짜를 추정하지 않는다. JSON schema_version 2는 10개 업무 필드와 별도 _meta를 내보낸다. 샘플 카탈로그의 내용 해시가 바뀌면 버전이 올라가고 새 공개 스냅샷으로 두 검색 저장소를 재색인한다.

## 2026-09-21 DB 카탈로그 및 관리 화면 통합

샘플의 정본은 이제 PostgreSQL `cm_sample_codes`이다. 검증된 JSON 300건을 한 번만 트랜잭션으로 이전하고 `cm_sample_bootstrap`에 출처 해시/건수/시각을 기록한다. 이후 시작·목록·대화·비교·검토·색인은 JSON을 다시 읽지 않는다. 재시작이나 JSON 변경이 DB 원문을 덮어쓰지 않는다. 실제 회사 등록 목록 `cm_codes`는 별도로 유지한다.

문서 관리에는 알림 DB 목록·검색·페이징·10개 필드 상세를 추가했다. 일반 파일 업로드·목록은 보존했다. 검색 테스트에는 DB 카탈로그 검색을 추가하고 기존 일반 문서 검색도 유지했다. `/api/code-catalog/search-test`는 원본 get_current_user 신원과 조회 제한을 검사하고 기존 UrstoryGateway의 임베딩/Nori/RRF/리랭킹 결과와 실제 단계를 반환한다. 대화처럼 설명 LLM을 추가 호출하지 않는 검색 진단 경로다. 샘플 비교·기획서 검토의 의미 검색도 동일한 DB 스코프의 게이트웨이를 사용한다. 원본 검색 설정·리랭킹 모델은 공유하고 데이터 스코프만 분리한다.

## 검색 화면 상태 유지

알림 DB 검색 결과·입력·목록 선택·상세 및 일반 문서 검색 결과·입력·옵션은 사용자 ID별 sessionStorage 키에 저장한다. 화면 이동 및 같은 탭 새로고침에서 복원하며 토큰은 저장하지 않는다. 탭을 닫으면 세션 보관이 종료된다. 저장소 접근이 제한되면 화면 자체는 메모리 상태로 계속 작동한다. 원본 수정은 `deploy/patch_search_persistence.mjs`의 고정 소스 계약 검사를 거친다.

## Langfuse 트레이스 응답 정규화

원본 모니터링 API가 반환하던 Langfuse 원문을 `code_agent.monitoring.normalize_trace`로 변환한다. timestamp → created_at, input/query → query, latency(초) → total_duration_ms(밀리초)를 연결한다. catalog-turn의 원문 미저장 정책은 유지하며 쿼리 대신 설명 라벨을 표시한다. output.status가 확인된 경우에만 성공/오류를 표시하고 상태가 없으면 unknown으로 둔다. 날짜·시간 누락/비정상값은 null 및 화면의 —로 표현한다. 목록과 상세에 동일 변환을 적용하고 기존 관리자 인증을 보존한다.

## 2026-09-22 Apple 온디바이스 판정 브리지

판정 모델은 `.env`의 `CODE_LLM_JUDGE_*`로만 정하고 관리자 화면에는 판정 칸을 두지 않는다(사용자 결정: 화면은 원래대로 대화 AI·검색 두 칸). 기본은 대화 AI가 검증도 맡는 것이며, 대화 AI가 Apple이면 `provider.judge_options()`가 판정도 Apple로 보낸다. 설정 API 응답의 `apple_judge_state`·`apple_judge_available`은 브리지 `/health`에서 읽은 준비 상태로, 화면이 Apple 대화 AI 항목을 켤지 정할 때 쓴다.

Apple 경로의 구성은 세 부분이다. `extensions/apple_bridge/applefm.swift`는 FoundationModels 프레임워크로 모델을 호출하는 표준 입출력 워커이고, `extensions/apple_bridge/bridge.py`는 127.0.0.1:8787에서 OpenAI 호환 `chat/completions`를 제공하며 공유 토큰(`CODE_APPLE_BRIDGE_TOKEN`)을 요구한다. `extensions/code_agent/apple_judge.py`는 원본 판정 프롬프트에서 근거와 답변 JSON을 꺼내 근거를 한국어 표찰 문장으로 다시 적고 답변을 줄 단위 주장으로 나눈 뒤, `메시지코드` 블록의 표찰 줄은 DB 원문과 문자 단위로 비교하고 자유 서술 줄만 모델에 구조화 출력으로 묻는다. 뒷받침되지 않는 주장이 하나라도 있으면 UNFAITHFUL/FAIL로 적어 차단한다. 판정 프롬프트·임계값·StrictJudge 검사는 원본 그대로이고, 생성·HyDE·재작성·RAGAS 평가는 바뀌지 않는다.

계약: 브리지는 `apple/on-device` 외의 모델명, 스트리밍, `json_object` 형식을 거절하고, 토큰 사용량을 추정해 넣지 않는다. 앱은 브리지에 닿지 못하면 503, 브리지 오류는 502, 형식이 어긋난 응답은 502로 중단하며 생성 모델로 되돌아가지 않는다. Docker 안의 API·worker는 compose의 `extra_hosts`(`host.docker.internal`)로 브리지에 접근한다. macOS에서 `manage.py start`는 브리지를 컴파일·기동하고(모델을 쓸 수 없으면 안내 후 계속, env로 강제했으면 중단), `stop`은 브리지도 내리고 `doctor`는 `apple_bridge` 항목을 보고한다. 판정 품질 실측은 TEST_REPORT의 2026-09-22 Apple 항목에 있다.
