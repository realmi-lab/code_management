# 알림 검색 설정 최적화 — 2026-09-21

실제 로컬 API와 PostgreSQL에 연결된 **분리된 합성 샘플 목록**으로 검사했습니다. 운영 코드 목록을 추가하거나 변경하지 않았습니다.

## 적용한 설정

- HyDE: 켜짐 → 꺼짐. 검색 전에 가상의 답을 생성하는 호출을 제거합니다.
- 멀티쿼리: 켜짐 → 꺼짐. 질문을 여러 표현으로 다시 생성하는 호출을 제거합니다.
- 로컬 E5 임베딩, 하이브리드 검색 0.5/0.5, 한국어 로컬 리랭커, 초기 후보 20개와 최종 후보 8개 유지.
- 개인정보 보호, 인젝션 차단, 숫자·근거 검증, 관리자 승인 유지.
- 검색 캐시 유지. 측정 중 일시적으로 껐다가 복구했습니다.
- 자동 청킹 1024/200 유지. 알림 레코드 검색을 위해 일반 문서 분할 설정을 변경하지 않았습니다.

## 측정 결과와 한계

`baseline.json`의 인증 대기 질문은 19.53초, `optimized.json`의 동일 질문은 10.45초였습니다. 모두 캐시 적중 없이 실제 검색 단계를 실행했고 첫 후보 AT-1923이 유지됐습니다. 단일 비교에서 약 46% 감소했으며 지속적인 평균 성능 보장은 아닙니다. 기존 요청은 multi_query 4.38초와 HyDE 5.22초를 사용했습니다.

최적화 설정의 다른 질문은 가입된 휴대폰 11.12초, 출금 한도 12.40초였습니다. 첫 후보는 각각 EX-0201과 SM-1120입니다. 출금 한도 질문에서 횟수 제한 문구가 상위에 나왔으므로 금액 한도 검색의 정확도를 검증한 것으로 해석하면 안 됩니다. 실제 데이터와 정답셋으로 추가 평가가 필요합니다.

CPU 4스레드는 독립 모델 검사에서는 빨랐지만 실제 API에서는 13.91/14.76/15.91초로 일관된 개선이 없었습니다. 따라서 CPU 스레드 제한은 제거하고 기존 자동 설정으로 복구했습니다. 해당 실험은 `rejected-4-thread-benchmark.json`, 독립 모델 검사는 `cpu-benchmark.json`에 기록합니다.

설치 검사 72개 통과. 이번 변경은 런타임 설정 변경이며 애플리케이션 알고리즘 변경은 없습니다. 모든 설정의 전역 최적값이나 운영 정답률을 입증하지 않습니다.

## 원복

이전 값은 `before.json`, 최종 설정은 `final-settings.json`입니다. 기존 관리자 설정 API에서 `hyde_enabled`와 `multi_query_enabled`를 true로 저장하면 이전 검색 확장 설정으로 돌아갑니다. 다른 설정은 일괄 덮어쓰지 않습니다.
