# 7·27·67번 실패 추적

원래 68문항 실행의 thread_id/request_id로 Docker의 구조화된 catalog_validation 로그를 연결했다. 원본 이벤트는 failure-trace.json에 저장했다. 처음부터 로그가 없었던 것이 아니라 외부 JSON event 문자열 안에 내부 JSON이 중첩되어 있어 두 단계로 파싱해야 했다.

| 문항 | 숫자 검사 | 원문 충실도 (기준 0.9) | 근거 검사 (기준 0.8) | 당시 차단 단계 |
|---|---|---|---|---|
| 7 | 통과 | 0.80 UNFAITHFUL | 0.83 PASS | 원문 충실도 |
| 27 | 통과 | 1.00 FAITHFUL | 0.57 FAIL | 근거 검사 |
| 67 | 통과 | 0.85 UNFAITHFUL | 0.80 PASS | 원문 충실도 |

27번에서 근거 검사 모델이 지적한 주장은 다음과 같다.
- 같은 노출 조건으로 나열된 코드들은 적용 메뉴만 다르다는 주장
- 등록 문구를 DB 원문으로 별도 확인해야 한다는 주장
- 카탈로그의 노출 조건 외에는 세부 비교 정보가 없다는 주장

7번의 별도 근거 검사에는 “등록 자료에 추가 분기 조건은 없습니다”라는 주장이 지적됐지만 이 검사는 PASS였다. 따라서 이것이 원문 충실도 차단의 직접 사유였다고 단정할 수 없다. 67번도 “등록 문구 원문은 DB에서 별도로 제공됩니다”를 근거 검사에서 지적했지만 PASS였다.

7·67번 원문 충실도의 상세 사유는 기존 로그에 빈 문자열로 남아 있다. 기존 기록 함수가 distortions:와 같은 줄의 내용만 수집해 다음 줄 목록을 놓칠 수 있는 결함을 발견했다. 실제 당시 모델 원문은 저장하지 않았으므로 누락 내용은 복구할 수 없고, 다음 줄 출력 때문이었다고 확정할 수도 없다.

## 수정 및 재확인

- 진단 로그 파서가 사유 필드의 다음 줄도 수집하되 다음 점수/판정 필드 전에 멈추도록 수정했다.
- 기존 개인정보·비밀 마스킹과 길이/개수 제한을 유지했다. 검증 프롬프트·임계값·차단 동작은 바꾸지 않았다.
- safety 회귀 검사 14개 통과. 실제 API 컨테이너에 반영했다.
- 세 질문을 새로운 demo 대화로 각각 1회 재실행했다. 세 문항 모두 통과했고 원문 충실도와 근거 점수는 모두 1.0이었다. 답변 시간은 7번 37.46초, 27번 52.78초, 67번 29.98초였다.
- 새 응답과 이벤트: failure-reproduction.json, failure-reproduction-trace.json.

## 결론과 한계

당시 실패는 DB 연결/숫자 검사가 아니라 생성 답변에 대한 LLM 검증 차단이다. 동일 질문의 재실행이 모두 통과해 지속적인 연결 장애는 관찰되지 않았다. 다만 새 답변과 새 판정을 동시에 생성했으므로 변동 원인을 생성 모델과 검증 모델 중 하나로 분리할 수는 없다. 최초 실패 답변 전문이 보관되지 않아 당시 판정의 정당성도 완전히 검토할 수 없다.

원래 68개 평가 결과는 수정하지 않았다. 이번 작업으로 수정한 것은 진단 사유 누락이며, 근거 검증의 변동성 자체를 해결했다고 주장하지 않는다.
